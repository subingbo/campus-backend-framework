## 2026-10-05 — 地点列表与地图快速跳转

### 完成内容

#### 1. 侧边栏地点列表（前端）

**文件：** `campus-web/src/views/MapWorkspaceView.vue`

- 在「添加地点」下方增加 **地点列表** 区域。
- **搜索框**：按名称、地址、分类、描述过滤，显示 `匹配数/总数`。

- **空状态**：无地点、无搜索结果分别提示。
- **布局**：列表区域可滚动；窄屏限制列表高度，保证地图仍可见。
- **交互**：
  - 点击列表项 → 地图飞到该点（zoom 18）、高亮标记、打开原有地点抽屉（评论/编辑逻辑不变）。
  - 点击地图标记 → 列表同步选中并滚动到对应项。

#### 3. 后端

## 2026-10-05 — 手机定位与以当前位置标记

### 背景与问题

地图工作台只能靠人工在地图上找位置：用户站在校园里想记录「我在这里」，得先自己在地图上认出所在位置再点击，没有定位能力也没有「我的位置」参照点。本次实现明确定位为 **Web 端定位**：手机浏览器通过局域网打开时受浏览器安全上下文限制，真正的手机端定位留给后续独立的 `campus-mobile`，本次先把「定位能力」与「地图能力」、以及客户端与后端的分层做出来。

### 完成内容

#### 1. 定位能力分层（前端）

**文件：** `campus-web/src/composables/useLocation.js`（新增）、`campus-web/src/composables/useAmap.js`

- 新增 `useLocation.js`：**定位能力层**，不引用任何高德标识。对外提供 `{ locating, location, error, summary, isCoarse, locate, reset }`，provider 契约是 `getCurrentPosition(): Promise<{ lng, lat, accuracy, locationType }>`。
- 该层负责：错误码 → 中文文案（权限拒绝 / 超时 / 不可用 / 不支持 / 组件未就绪）、`describeLocation()` 精度文案、`isCoarseLocation()`（IP 定位或误差 > 200m 视为粗定位）、重复点击保护；UI 提示不放在这一层。
- `useAmap.js` 保持**地图层**职责（地图、marker、镜头、地图点击），新增高德定位适配器 `createAmapLocationProvider()`，把 `AMap.Geolocation` 收敛成上面的 provider 契约；插件列表加入 `AMap.Geolocation`，内置定位 UI 全部关闭（标记与镜头自管）。
- 坐标系：定位结果经 `convert: true` 从 WGS84 修正为 **GCJ-02**，与高德底图一致，避免手机原生 GPS 直接打点偏移几十到上百米。
- 定位组件初始化失败只降级定位能力（try/catch 返回 null），不影响地图本身可用。

#### 2. 「我的位置」标记（前端）

**文件：** `campus-web/src/composables/useAmap.js`、`campus-web/src/views/MapWorkspaceView.vue`

- `createPlaceMarkerController` 新增 `setMyLocation(location, { panTo })` 与 `clearMyLocation()`。
- `render()` 内的 `map.clearMap()` 会清掉全部覆盖物，因此在渲染地点之后重新挂载「我的位置」标记，保证刷新或增删地点不会把参照点清掉。
- 标记样式与地点标记区分：绿色圆点（带半透明光晕）+「我的位置」标签；`anchor: 'center'` 让圆点正落在坐标上（地点标记用的是 `bottom-center`）。

#### 3. 工作台定位交互（前端）

**文件：** `campus-web/src/views/MapWorkspaceView.vue`

- **定位到我**（所有成员可见）：定位 → 地图打「我的位置」标记 → `setZoomAndCenter(17, …)` → 提示精度，不落点；查看权限只能看自己在哪。
- **以我的位置选点**（编辑/群主）：定位成功后进入原有选点模式，用户在附近点击地图，沿用原有添加弹窗。
- **标记我的位置**（编辑/群主）：定位成功后预填经纬度（分类为空时补默认分类）并打开原有添加弹窗，名称与分类仍由用户填写，走原有 `submitAdd` 提交。
- 添加弹窗坐标区新增 **填入当前位置**（不移动地图，不覆盖已选分类）。
- 粗定位诚实处理：`location_type === 'ip'` 或精度 > 200m 时用 warning 提示「精度较低，请确认位置是否准确」，不当成精确定位。
- 定位失败（拒绝授权、超时、非 HTTPS 局域网地址）统一用 `ElMessage` 说明原因，并附加「当前页面不是 HTTPS/localhost」提示；不做证书服务。

#### 4. 后端：本次无改动

- 继续使用 `POST /maps/{id}/places`，无新增接口、无表结构变更。
- 核实结论：后端与数据库**未绑定任何地图厂商**（无 amap/gcj/coordType 等字段或依赖）；5m 融合已在服务端（`GeoCandidateQuery` + `GeoUtils` Haversine，`PlaceServiceImpl` / `SharedMapServiceImpl` 的 `MERGE_RADIUS_METERS = 5.0`），Web 与将来的手机端天然共用同一判定。
- 遗留：`db/schema.sql` 中 `place.longitude/latitude` 的列注释仍写 `WGS84`，与实际写入的 GCJ-02 不一致，本次按「不改后端」只记录待办。

#### 5. 仓库整理与提交

- `.gitignore` 补齐 `node_modules/`、`campus-web/dist/`（此前缺失，`campus-web/node_modules` 约 126MB 会被误提交），并忽略扫描产物 `.mimosa/` 与本地编辑器规则 `.cursor/`。
- 将仓库中尚未入库的项目源码（`campus-web` 前端、后端增量包与 mapper、测试、schema/data、README、docker-compose、移除的两个 probe 控制器）连同本文档一并提交并推送到 `origin/main`。
- 凭据：真实高德 key 只在被忽略的 `campus-web/.env`，仓库内 `.env.example` 为占位符；`application-dev.yml` 与 `docker-compose.yml` 中的口令是此前提交中已存在的本地开发值，本次未新增任何凭据。

### 验证情况

- `campus-web` 执行 `npm run build` 通过（1684 modules，产物 `dist/assets/index-*.js` 约 1.14MB / gzip 377KB）。
- 代码核对：`render()` 的 `clearMap()` 之后重新挂载「我的位置」；`useLocation.js` 不含任何 AMap 标识，与地图层互不 import，由视图通过 `useLocation(() => locationProvider)` 组合。

## 2026-10-07 — 聊天面板自适应修复

### 背景与问题

工作台的聊天浮层在部分窗口尺寸下会被屏幕裁掉一部分。排查出三个根因：

1. **全局缺 `border-box` 重置**：工作台侧栏是 content-box，`max-height: 100vh` 加上下 16px 内边距使实际总高 932px，把网格行撑得比视口高 32px——贴面板底部的聊天面板随之有约 20px 在视口外（桌面端也存在，是页面轻微可滚动的根因）。
2. 手机端聊天面板 `position: absolute` 锚在地图容器里（单列布局下地图在页面下方），随页面滚动，视口位置不可控；且面板高 62vh 比地图容器 60vh 还高，顶端会伸出容器。
3. 手机/桌面样式切换依赖 JS 的 `isMobile`（matchMedia）加 class，窗口跨断点时事件有延迟，切换瞬间沿用旧布局。

### 完成内容

**文件：** `campus-web/src/App.vue`、`campus-web/src/views/MapWorkspaceView.vue`

- `App.vue` 全局补 `*, *::before, *::after { box-sizing: border-box }`，消除 padding 撑破 max-height/width 这一类问题。
- 聊天面板手机端改 `position: fixed` 视口底部停靠（`left/right/bottom: 12px`，高 `62dvh` 回退 `62vh`）：不随页面滚动、不被容器裁切，打开即在视野内；桌面保持 absolute 右侧全高。
- 手机/桌面布局切换改由 **CSS 媒体查询**承担（≤768px），移除 `.chat-float--mobile` class 与 `isMobile` 依赖及随之无用的 `chatFloatRef` / `scrollChatIntoView`；桌面宽度钳制 `width: min(340px, calc(100% - 24px))`。

### 验证情况

- 桌面 1440×900：页面高度恢复 900=视口（docH 由 932 → 900），聊天面板 bottom 888 完全可见。
- 窄桌面 900×800：面板 340px 收进地图区（fits: true）。
- 手机 390×844：`position: fixed` 底部停靠（x=12、bottom=832=视口-12），滚动页面位置不动，始终完整可见。
- `npm run build` 通过（6.87s）。

## 2026-10-06 — 校园社交一期：好友 + 聊天与地图融合（WebSocket 实时层）

### 背景与问题

按产品设想把项目从「校园地图工具」升级为「基于地图的校园社交平台」：聊天必须和地图发生关系，而不是做一个孤立的聊天软件。本期落地「社交 + 实时」两层：好友、私聊、地图群聊、地点聊天室、在线状态、正在输入、地点变更实时推送、未读数。共享地图的协同维护（OWNER/EDITOR/VIEWER）此前已具备，本期补齐人与人的关系链与实时通信层。

### 完成内容

#### 1. 数据库（6 张新表，纯新增）

**文件：** `src/main/resources/db/schema.sql`

- `friend_request`（from/to/status 0待1同2拒/验证留言）、`friend`（好友关系，双向行，uk_user_friend）、`conversation`（type PRIVATE/GROUP/PLACE，可绑 map_id/place_id）、`conversation_member`（uk_conv_user）、`message`（会话/发送者/内容/类型，idx conv_created）。无外键、`uk_`/`idx_` 命名与既有表一致；增量已对运行库执行，schema.sql 同步更新保证新环境可重建。

#### 2. 好友体系（REST）

**文件：** `com.campus.social`（entity/mapper/XML/dto/service/controller）

- `FriendController /api/friends`：搜索用户（按用户名/昵称 LIKE，返回是否已是好友/已申请）、发申请、收/发请求列表、接受、拒绝、好友列表（带在线状态）、删除好友。
- 申请与接受通过 WS 实时推送：`FRIEND_REQUEST`（对方在线时即时弹通知、请求列表自动刷新）、`FRIEND_ACCEPTED`。

#### 3. 会话与消息（REST + 持久化）

**文件：** `ConversationController /api/conversations`、`ConversationServiceImpl`、`ChatMessageService`

- 三类会话懒创建：私聊（仅好友，按双人查重）、地图群聊（每图一个，进入时幂等同步地图成员）、地点聊天室（每地点一个，全校可见——任何登录用户可进，符合「地点是公共内容载体」）。
- 会话列表带标题解析（私聊对方昵称/地图名/地点名）、最后一条消息、未读数；历史消息分页（读取即清零该会话未读）。
- 发送链路：访问校验（PRIVATE=仍为好友、GROUP=地图成员、PLACE=登录）→ MySQL 落库 → 在线成员实时推送 → 离线成员未读 Redis 计数（`social:unread:{userId}:{convId}`）。

#### 4. WebSocket 实时层（原生 WS + 自定义 JSON 协议）

**文件：** `com.campus.ws`（WebSocketConfig / WsHandshakeInterceptor / ChatWebSocketHandler / WsSessionRegistry / MapEventNotifier），`pom.xml` 加 `spring-boot-starter-websocket`，`SecurityConfig` 放行 `/ws/**`

- 端点 `/ws?token=<accessToken>`（浏览器无法给 WS 设 header）：握手拦截器复用 `JwtTokenProvider` 校验并拒绝 refresh 型/黑名单 token，userId 写入 session attributes（异步会话不经过 SecurityContext）。
- 上行帧 `CHAT_SEND / TYPING / READ / PING`；下行帧 `CHAT_MESSAGE / TYPING / PRESENCE / FRIEND_REQUEST / FRIEND_ACCEPTED / PLACE_CHANGED / UNREAD / ERROR / PONG`。
- `WsSessionRegistry`：userId → 多端会话集合（多标签页），在线状态写 Redis SET `social:online`，好友上下线广播 `PRESENCE`；应用层 30s 心跳防代理断连，前端指数退避重连。

#### 5. 地图事件 → 实时通知

**文件：** `MapEventNotifier` + `SharedMapServiceImpl` / `PlaceServiceImpl` hook、`MapPlaceMapper.selectMapIdsByPlaceId`

- 地点被添加/分享/关联（同走 `insertMapPlace` 单一入口）、移除、评论、修改（按 place 反查所属全部地图）时，`PLACE_CHANGED` 帧推送给该地图的在线成员（操作者除外），前端 toast「XX 把地点加进了地图『YY』」并自动刷新当前地图地点列表。通知器只依赖会话注册表与 mapper，不与业务 service 相互依赖。

#### 6. 前端

**文件：** `campus-web/src/composables/useChatSocket.js`（全局单例 WS：重连/订阅/心跳/从 JWT 解析当前用户）、`src/components/ChatPanel.vue`（气泡消息列表＋Enter 发送＋正在输入提示，三种会话复用）、`src/views/FriendsView.vue`（新路由 `/friends`：搜索加好友、请求处理、好友在线绿点、私聊对话框）、`MapListView` topbar 好友入口（待处理请求红点徽标）、`MapWorkspaceView`（侧栏聊天按钮 → 聊天浮层：桌面右侧栏/手机底部停靠面板，tab「地图群聊/地点聊天」，地点抽屉与手机浮窗均有「地点聊天」直达；`PLACE_CHANGED` toast＋刷新；手机端打开聊天自动滚入视野）、`vite.config.js` 加 `/ws` 代理、`api/index.js` 加 friendApi/chatApi。

## 2026-10-14 — 后端拆分为 campus-framework / campus-server 双模块

### 背景与问题

后端一直只有一条主线：本仓库最初是脚手架的副本（首个提交 `68be1ec` 与脚手架仓库一致），脚手架代码（认证、安全、RBAC、统一返回体/异常/限流）与自己写的业务代码（地点、帖子、共享地图、社交、活动、举报、搜索、管理端、WebSocket）全在同一个 Maven 模块 `campus-server` 里，接口分不清哪些是脚手架给的、哪些是业务新增；依赖上还有两处「框架反向引用业务」（`UserServiceImpl` 注入 `PostMapper`/`PostLikeMapper` 统计用户主页，`common.geo` 引用 `place` 实体），一处不改就无法拆分。

本次把后端拆成两个 Maven 模块，**对外行为零变化**：接口路径、返回结构、数据库、前端、Docker 全部不动，只改工程结构。

### 完成内容

#### 1. 多模块骨架

**文件：** `pom.xml`（改为聚合父 POM，`packaging=pom`）、`campus-framework/pom.xml`（新增）、`campus-server/pom.xml`（新增）

- 父 POM 里该插件默认 `skip=true`，只有可执行模块关掉——否则 `mvn -pl campus-server -am spring-boot:run` 会在聚合器上报「找不到 main class」。

### 完成内容

#### 1. 格网命名锁防重（R1 → 已修复）

- 新增 `place/lock/PlaceGridLock`：MySQL `GET_LOCK` 命名锁九宫格（单元 0.0001°，纬向约 11m、经向 ≥10m，均大于 5m 合并半径 ⇒ 相距 ≤5m 的两点必共享 3×3 邻格之一）；键按字典序逐个加锁防交叉等待，等待超时抛 429「地点写入繁忙」。
- `PlaceMapper` 增 `getLock/releaseLock` 两个 `@Select` 注解方法（与业务复用同一事务连接）；`PlaceServiceImpl.createPlace` 改为"加锁 → 锁内复检（照旧 bbox 粗筛 + Haversine 精算，不取整）→ 插入"，`PlanSaveService.ensurePlace` 复用入口自动受益；**零表结构变更**。
- **放锁时机是正确性关键**：`GET_LOCK` 是会话锁不是事务锁，用 `TransactionSynchronization.afterCompletion` 在提交/回滚完成后统一释放——杜绝"复检查不到未提交行"的窗口。
- **踩坑（实测定论）**：仅"提交后放锁"还不够——默认 REPEATABLE READ 下，并发线程在加锁前的 `validateCategory` 读就把一致性视图钉死在事务起点，拿到锁后复检看不到前一事务刚提交的行，实测 10 并发出 5 条重复。`createPlace` 显式 `READ_COMMITTED`（每条语句读最新已提交数据）后闭合。

#### 2. 保存版本竞赛防护（R6 → 已修复）

- `/plan/save` 支持**可选** body `{"expectedPlanVersion":N}`（不传兼容现有前端）；`PlanSaveService` 行锁内：幂等命中优先返回既有活动（不覆盖新版）→ 版本不一致抛 **409**「草稿已更新，请刷新后重新保存」→ 过了才重新校验草稿并落库。
- 框架层：`ResultCode` 增 `CONFLICT(409,"数据已变更，请刷新后重试")`，`GlobalExceptionHandler.mapHttpStatus` 增 `case 409`（否则 409 会落 default 变 500）。

#### 3. `PlanSaveConcurrencyAcceptanceTest`（DB-01～08 全绿）

- **DB-01** 顺序双存同 activityId；**DB-02** 服务层 10 线程并发 `save(expected=1)` → 恰 1 条 activity + 1 组 stops，10 个响应同 id；**DB-03** `ActivityStopMapper.insert` 注入异常 → 活动 0 条、会话仍 DRAFT、ensurePlace 建的 place 随事务回滚零残留；**DB-04** 版本竞赛三不变式：至多创建一个活动、冲突消息必为「草稿已更新」、活动标题必属 v2 草稿（HTTP 侧另验 409→新版本成功→SAVED 后旧行幂等返回）；**DB-05** 10 线程并发同坐标 `createPlace` → 恰 1 条 place，其余 pendingDuplicate 且候选指向同一条；**DB-06** 3 站活动 PUT 改 2 站 → 站点整体替换且 seq 1、2 连续；**DB-07** 站点早于开始 / 缺坐标 / 9 站超限全 400 且 `/mine` 依旧空；**DB-08** 无 stops 单站老流程创建/编辑/查询兼容。

### 修复（全部按评审口径落地）

1. **冲突精确豁免 + 谱系活动**（评审①②）
   - `PlanDto.lineageActivityId`：仅 `revise` 在“已保存会话+真实内容变化（且未显式 asNewDraft）”时

   - `revise` 等值内容不升版；`asNewDraft=true`（显式“复制为新草稿”）→ 清空谱系 → 再保存新建。

     `sourceType=ACTIVITY && sourceId==lineageActivityId`——本人**其他**活动（如 14-16 篮球 vs 新规划

     `busyEnd + headBuffer`（“14:00 下课不能 14:05 到 30 分钟外的咖啡店”→ 14:10 起或无解说明）；

   - 保存校验：已知忙闲与活动窗口**重叠**或**头/尾相距 < 10 分钟**（衔接缓冲）→ 409（豁免仅谱系活动）。
4. **planningSourceVersion 覆盖备注**：`PlaceCommentMapper.selectDigestByMaps`
   （MAX(id)+COUNT per (map,place)）进入指纹——加/删备注都会让草稿保存时 409 重新确认。
5. **ThreadLocal 审计**（评审④，结论）：`AgentService/AgentToolkit/LlmClient` 无 CompletableFuture/
   @Async/new Thread；工具调用都在触发 run 的同一 agent-group 线程内同步执行；
   `GroupAgentService` 在 finally 清理 GROUP_CONTEXT；SSE 个人线程只读 SecurityUtils 不触群上下文；
   两个群并发 @AI 各自独立 run，set/clear 线程边界无交叠。显式 AgentExecutionContext 重构列为长期项。

## 2026-10-20 — Agent Trace P1-G 数据边界修复与 P1 冻结

### 背景

P1 功能测试已通过，但代码勘察发现四个边界会让 P2 回放误判“完整”：
`complete` 未计入 writer pending、pending/drop 计数器存在并发竞态、队列满时关键事件可能越过前面的队列事件、
`droppedCount>0` 仍可能返回 `KNOWN` 成本。本轮先修边界，再做浏览器冒烟并冻结 P1。

### 修复内容

- `AgentTraceWriter`：
  - pending/dropped 计数改为 `ConcurrentHashMap<String, Long>` + 原子 `compute`，入队前先计数；
  - 关键事件在队列满时先做默认 500ms 有界等待（`critical-offer-timeout-ms`），优先排在已入队事件之后；
    只有超时才同步 fallback，并记录可能的 seq 顺序偏移告警；
  - 暴露 `pendingDroppedCount`，drop flush 只减去快照值，保留并发新增。
- `complete`：统一为 `COMPLETED + effective dropped=0 + pendingEvents=0`；列表/详情/JSONL meta 共用。
- `AgentTraceExportService`：注入 writer，`trace/meta` 增加 `lastSeq/pendingEvents`，`droppedCount` 用 effective 值。
- `session/end` 的 `droppedCount` 使用 effective 值，避免终态事件带过期丢弃计数。
- 成本新增 `PARTIAL`：effective dropped>0 时金额为 null，优先级 `DISABLED → PARTIAL → UNKNOWN_MODEL → UNKNOWN_RATE → UNKNOWN_TOKENS → KNOWN`。
- 前端：`pendingEvents>0` 显示“同步中”；修复 `LocalDateTime` 数组格式在 Trace 页面显示为 `2026,10,19,...` 的问题。

### 浏览器冒烟（真实本地 MySQL/Redis/后端/Vite）

- 登录 admin → `/traces` 列表：模型、耗时、Token、成本、事件/工具、完整性、时间显示正常；
- 旧 Trace 成本显示“不可估算”，原因“模型信息不完整（旧 Trace 或混合模型）”；

- 临时 RUNNING 会话验证列表 8 秒自动刷新为 COMPLETED、详情尾部补拉至 2 条事件后显示“已同步”，验证后已清理。

## 2026-10-20 — Agent Trace P2-A 执行链模型与组装器

### 目标

在 P1 事件基础上建立只读执行链，供后续 P2-B 回放复用。本轮不建快照表、不加 API/UI、不调用 LLM/高德，
不修改规划算法。

### 实现

新增 `campus-server/src/main/java/com/campus/ai/trace/execution/`：

- `TraceExecutionNodeKind`、`TraceLinkConfidence`、`TraceExecutionNode`；
- `TraceExecutionDiagnostics`、`TraceExecutionAssembly`；
- `TraceExecutionAssembler`：纯函数，输入 `List<AgentTraceEvent>`，按 `seq` 排序后组装。

关键规则：

- SESSION → RUN（按 traceId）→ STREAM/TURN/STEP；保存/修订无 step，直接挂 RUN，不并入聊天最后一步；
- 工具按 `callId` FIFO 配对；无 callId 用 `(traceId,turn,step,tool,ordinal)`；同名工具不合并；
- LLM 无 callId，按 `(traceId,turn,step)` FIFO 配对 request/response/error；
- 规划事件按 draftVersion/operation/seq 结构化；`plan/confirm` 无 RUNNING 是幂等保存的正常情况；
- 缺 start/end 保留 `hasStart/hasEnd=false`；未知事件保留 UNKNOWN；seq gap、重复 callId、orphan business、
  payload 解析失败全部进入诊断；
- 节点 `attributes` 使用显式白名单，不复制正文/地点/坐标/日程/密钥；数字保持 Long，不因三元表达式变成 10.0。

### 测试

新增 `TraceExecutionAssemblerTest` 7/7：

1. 完整 chat + LLM + tool + plan 链；
2. 工具缺终止事件不伪造成功；
3. LLM response 缺 request；
4. 重复 callId/同名工具不合并；
5. save/revise RUN 与 chat STEP 分离；
6. seq gap/未知/敏感 payload/orphan/trace partial；
7. 2500 步、10004 事件的稳定组装与重复组装一致性。

全量回归：`mvn -pl campus-server -am test` → **131/131 通过**（0 失败/0 错误/0 跳过）。

### 文档

- 新增 `docs/agent-trace/execution-model.md`：节点类型、字段、配对规则、诊断、缺失处理、属性白名单；
- 更新 `README.md`、`实施完成情况与待办.md`。

### 边界

- 本轮不提供 HTTP 接口；P2-B 再接 `getExecution`/replay API。
- 不宣称 LLM→tool 的因果级关联；只有 callId/step 结构证据。
